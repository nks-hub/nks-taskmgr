# How it works

Detailed behavior of the views, helpers and native API. Back to [README](../README.md).

Switch between Processes and Performance using the left navigation. Performance keeps individual resource previews beside the graph, hardware facts, and process cards. Select a process card to open its row in the process table. The refresh control switches between one second and 250 milliseconds; Pause stops both collectors. Graphs switch between 60 seconds and 10 minutes. Ctrl+F opens the process search.

Processes provides All, Active, and Tree views. Search accepts process names and PIDs, including case-insensitive Unicode names. Click a column heading to sort, drag headings to reorder columns, and use Ctrl or Shift to select multiple rows. Tree branches expand by clicking their arrow or pressing the left and right arrow keys. Overview cards open the corresponding system resource.

The WinUI candidate also resizes columns by dragging their edges and hides optional columns through the Columns menu. A heading's context menu offers move and resize commands for keyboard use. The menu restores the default layout; the process name remains visible.

The save icon in the WinUI process toolbar opens a snapshot preview. Choose CPU, memory, process I/O, and device fields. Process and device names and raw device identifiers have separate opt-ins and are excluded by default. Command lines, arguments, accounts, and hardware fact strings are not exported. Values retain their units, sources, sample states, and process lifetime keys. The sample is captured before the dialog opens; live updates do not change it. Saving runs outside the UI thread and preserves an existing destination's access rules.

The comparison icon opens a separate window. Select the original and following JSON snapshots, then choose Compare. Their order follows your selection, even if the recorded wall clock moves backwards. The result lists process changes and shows the selected process's values, sample states, sources, and differences. Numeric differences require valid values with matching units and sources. When a process lifetime cannot be verified, the result explains why it cannot be compared. The window is read-only, accepts exports without names, and can cancel loading or comparison.

Process rows are 34 DIP high with 13 DIP text. The UI uses Segoe UI Variable when installed and Segoe UI otherwise. WinUI reads executable icons through up to two child processes after verifying process creation time. Waiting for a response is limited to three seconds; a silent worker is terminated and restarted for the next request. The workers inherit the user's permissions and exit with the application. Unavailable icons use a generic symbol, and the cache holds up to 128 images. The Win32 candidate currently uses letter icons.

While the pointer is over a process row, the table keeps its row order and updates the counters. New processes appear after the pointer leaves. A finished process remains marked until then and cannot become a live selection. Switching to Performance and back preserves the scrolled process position.

The memory page separates physical memory, commit, and pagefile usage. Pagefile usage comes from `EnumPageFilesW`; it is not a measure of paging I/O activity. Network graphs show receive and transmit values in bits per second.

WinUI graphs label their value and time scales. Auto scale follows the highest retained sample; disabling it restores the device capacity or 100 percent. Hover reads measured samples, click pins a time, and the arrow keys move through history. Enter toggles pinning and Escape returns to the live graph. Logical CPU charts adapt to the processor count and panel width.

Detailed graphs share their cursor and pinned time. Shift-click or Shift-Enter selects two interval endpoints; Escape clears the selection. Receiving charts show a cursor line without opening extra tooltips. The Processes at time button opens a separate historical view only on request. It displays retained process samples and their actual timestamps, omitted data, and gaps. Process I/O is not attributed to the selected physical disk, network adapter, or GPU. Historical rows never invoke live process actions.

The WinUI Hardware view (Sestava) lists CPU topology, caches and CPUID fields, SMBIOS memory speed and slots, motherboard and BIOS names, and UPS data exposed by the Windows battery driver. Firmware omissions remain unavailable. UPS polling runs on the resource collector every five seconds and uses read queries. SPD timings and vendor-specific UPS protocols are not implemented. Network details distinguish link speed from current receive and transmit traffic.

GPU details use the busiest engine for overall utilization. The WinUI view selects four engine graphs independently; the Win32 view lists all available engines. Memory graphs separate dedicated and shared usage. Process cards appear under CPU and physical memory; disk, network, and GPU details do not substitute CPU rankings for device activity.

Disk performance counters refresh with the device view. SMART and temperature queries refresh every 30 seconds and open devices with no read/write access requested. NVMe health comes from the standard log page; other supported drives expose failure prediction and storage temperature queries. Missing or denied data stays unavailable. These queries do not install drivers or request elevation.

Services runs in read-only mode. Its collector starts when the view opens and refreshes state once per second; polling pauses while the window is minimized. List configuration is cached for up to 15 seconds. The selected configuration is queried again with its detail. The dependency list opens a known service on double-click or Enter. Windows may omit services that the current account cannot query; denied configuration and host identity queries remain unavailable.

The WinUI Shared PID filter shows services that report the same nonzero host PID. The selected detail lists the other reported services, their states, and their accounts. This grouping follows the SCM snapshot; opening a live host process separately requires its verified lifetime identity.

Process details opens from the WinUI process toolbar for a selected live process. Its thread and module lists are read-only. File signature checks run only when requested for a selected module and use cached local trust data. The worker has the same permissions as the application, a bounded request queue, a five-second operation deadline, and cancellation that closes its own job.

The Memory and Handles tabs filter their loaded data. A handle's type and name are queried on request and describe the duplicated object observed at that time. Global object search starts explicitly from the process toolbar and reports its progress, skipped owners, and limits. It matches local DOS and NT path forms, batches results, and marks incomplete searches. Opening a live owner requires its full current process lifetime key. Repeated queries share at most two worker processes with two queued requests.

The Hardware view includes a capability panel. It shows current measurement states, the last targeted read query, and the application's effective elevation state. Selecting a feature explains ordinary access, elevated access, and the required provider. CPU temperature has an opt-in reader for a local HTTP API compatible with LibreHardwareMonitor. It reads timestamped CPU temperature metrics from 127.0.0.1:8085 at most once every five seconds while enabled, without starting a provider, driver, or elevated process. The provider identity is not authenticated. The view names the source, sensor ID, publication time, and age; missing or stale data is not a measured zero. The endpoint follows the [upstream HTTP contract](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/blob/1d74d0ea012cacbcdf858ab9c5dd8a862b25d6e6/LibreHardwareMonitor.Windows.Forms/Utilities/HttpServer.cs).

The Applications view inventories visible windows only while that view is selected. It verifies each window owner's process lifetime and separates packaged application owners from their frame hosts. Ambiguous matches are skipped and reported as incomplete. Selecting a group keeps its member process table on the same screen; working sets are not summed into a group memory total.

The native frame API also supplies added, changed, and removed process keys with a revision and base revision. WinUI applies these batches to existing row objects and rebuilds ordering only when membership or a relevant sort or filter value changes. The Win32 table merges changed order keys and redraws affected rows without clearing an unchanged selection. A missing baseline or an older DLL falls back to the full snapshot. Full frame data remains available for other consumers.

The native DLL and desktop require `nks-collector-worker.exe` beside their binaries. Process, device, and service workers inherit the application's permissions and each run in a separate job with a 256 MiB process memory limit. The parent retains CPU sampling state and bounds replies to 64 MiB. It waits for a retiring worker to exit before starting its replacement.

The WinUI process toolbar opens an ETW event window. Opening the window starts no session. Starting a log replaces its displayed history and may fail if Windows denies access. Process start and stop events use the manifest payload creation time when available; an event PID alone never becomes a current process lifetime key. The transfer view upserts observed disk, TCP, and UDP windows by sample ID and attribution epoch. Correlated or unknown ownership stays partial and does not establish a process total or a valid rate. The source bounds identity and transfer storage to 8 MiB and reports loss, eviction, late events, and resynchronization. The UI bounds retained rows and its estimated data budget. A failed stop retains the session lease and its cleanup state; the application waits up to five seconds before offering a close with unconfirmed cleanup.

The lifetime view joins start and stop events only when their verified boot ID, PID, and creation time match within one capture segment. Unverified events remain separate. Duration requires a valid pair of monotonic timestamps; an absent stop event does not establish that the process is still running. Rows report gaps, late events, duplicate or conflicting endpoints, and available exit codes. The lifetime store holds at most 4096 rows; all three modes and the held view share an estimated 11 MiB data budget.

Process actions use `nks-actions-worker.exe` in the application's directory, with the same permissions as the application. An ordinary request contains at most 64 full process lifetime keys and creation times. The helper checks its actual parent, target identity, owner, session, critical status, and protection state before each action. It refuses system, protected, critical, and different-user or different-session targets. Tree termination accepts one root and keeps a plan of at most 256 lifetimes across three bounded inventory passes. It reports unattempted targets, limits, and uncertain remainder separately, and never claims atomic tree termination. The client permits one outstanding request and waits at most five seconds; a timeout can leave the action outcome unknown and is never retried automatically. A retiring helper must exit before another request starts.

The process action menu also edits default CPU Sets across processor groups, with a separate reset option. A preview shows group and logical-processor numbers and the current selection. The worker binds the selection to the process lifetime, topology, and previous defaults, then reads back the result. Default CPU Sets respect explicit thread selections and hard affinity; they do not prove where a thread ran. See the [Windows CPU Sets documentation](https://learn.microsoft.com/en-us/windows/win32/procthread/cpu-sets).

The separate elevated process-action menu uses `nks-elevation-broker.exe`. The GUI, bridge, and elevated server check the configured publisher key, signed image identity, actual peer processes, and local logon session. Each elevated batch requires its own administrator confirmation. System, critical, protected, and different-session targets remain refused. A build without a publisher pin refuses the request before starting the bridge or UAC. Configure the public SHA-256 SPKI pin through `scripts/build.ps1 -BrokerPublisherSpkiSha256 <64-hex-digits>`; the script forwards the same value to native code and WinUI assembly metadata. The application and broker must also carry valid signatures from that publisher.

Service control uses a separate `nks-service-actions-worker.exe`. Its read-only plan holds up to 64 service objects while the user confirms the operation and active dependents. Applying the plan checks the configuration and state again, stops dependents before their parent, and observes service checkpoints within a shared 30-second deadline. Restart restores the approved services that were previously running; paused or pending dependents are refused. Configuration changes, failed operations, and incomplete transitions are reported without automatic retry.

The dump command uses the operating system's DbgHelp through `nks-dump-worker.exe` or `nks-dump-worker-x86.exe`, matching the selected process architecture. Both helpers link the C++ runtime statically. Full-memory capture is off by default. The client holds the destination directory and a uniquely created temporary file; the worker receives a duplicate of that file handle and returns its identity, size, and SHA-256. Publication follows complete response validation and helper exit, uses a flush and rename without replacement, and never deletes a file by a guessed path. Capture has a 60-second deadline and a 32 GiB file limit.

The Dump menu also opens unfinished captures without requiring a selected process. A private journal records the temporary file and helper identity before capture and records the verified hash before publication. Recovery runs only on request. It preserves unknown or unverifiable entries, refuses changes while the original GUI or helper may still be alive, and asks before completing or removing an owned temporary file. A published final dump has no recovery deletion path. Journal storage is limited to 64 entries and 1 MiB.

The application does not expose a plugin API or scan extension folders. Helpers accept only their fixed protocol commands. Their runtime DLL search uses the application directory and Windows system directory; the dump helpers use only the system directory. Linker flags also restrict static import resolution. This follows the documented [Windows DLL search controls](https://learn.microsoft.com/en-us/cpp/build/reference/dependentloadflag).

The Updates button opens the local installer inventory. Adding an installer verifies and caches it without installing. A prepared update requires the signed installer for the current exact version and revision as a rollback baseline. Confirmation names the current, selected, and rollback versions. The worker waits up to 30 seconds for the GUI to exit before launching the held, verified setup in the original installed or portable mode. It does not request elevation or force other processes to close. Installer success is followed by a check of the installed application. Settings outside the installation directory are preserved.

The Updates window also asks the GitHub Releases API for the latest non-prerelease version. A newer release must carry a setup named for the same version under the repository download path. The setup is downloaded into the user profile, held open without write sharing, and started only after WinVerifyTrust accepts the chain, the signer SPKI matches the update pin, and the version resource names the setup role and the release version. It runs `/SILENT` in the mode of the running copy (`/ALLUSERS` for Program Files, which elevates through Setup, or `/CURRENTUSER`), waits for the GUI process given by `/NKSWAITPID`, and with `/NKSRELAUNCH=1` starts the application again as the original user. The GUI exits right after starting Setup. Portable copies and builds without the update pin only link to the release page. The main window makes one such check 20 seconds after start and highlights the Updates button when a newer release exists.

The updater uses a separate `UpdatePublisherSpkiSha256` build property and native `NKS_UPDATE_PUBLISHER_SPKI_SHA256` value. An empty pin refuses update operations before a helper starts. The signing workflow sets both publisher pins from the selected certificate. The installer attempts a cache-only registration of itself after installation; unsigned development installs remain usable if that step is refused. Portable ZIPs include a product marker. Portable updates require that marker, preserve the selected directory, and create no uninstaller registration or application shortcuts. Registered installations require the actual current-user Inno registration. Plans and rollback history bind the directory volume and file ID; an unrecognized root remains read-only.

Unresolved operations appear in a separate recovery selector. Recovery requires an explicit plan using the verified original installer. A live or unverifiable worker or installer prevents repair. New journals store the installer lifetime before its suspended process is resumed; journal publication uses a flushed temporary file and a rename without replacement. Only a new verified repair resolves the old record, including a chain of failed repairs. Legacy records without an installer identity remain read-only in the same Windows boot.

Cache cleanup shows a preview before a separate confirmation. The worker retains current and previous packages for known application roots, live operations, recovery evidence, and unknown data. It rechecks owned files through held handles before deletion and skips changed or busy items. Results distinguish confirmed deletion, skipped items, and unknown sizes. Cleanup does not close the GUI or launch an installer.

The WinUI Appearance menu selects the system, light, or dark appearance and saves the choice in the user profile. Theme changes update existing controls, charts, and dialogs. Missing or stale measurements are labeled rather than displayed as measured zero. The Performance view can include virtual network interfaces and loopback; the default view keeps physical adapters, including disconnected ones. This view filter preserves LUID identities and retained history. WinUI saves the preference in the user profile.

Capture two real process samples one second apart:

```powershell
./build/msvc/Release/nks-sample.exe
```

The JSON result contains the process count, logical processor count, system CPU state, physical memory, and collection duration. Process I/O counters represent I/O issued by a process; they are not per-disk or network traffic measurements.

Process identity uses the full 128-bit Windows boot identifier with the PID and generation. `nks_frame_get_boot_data` returns both identifier halves and their availability state. The ABI v1 `boot_time` field remains wall-clock metadata and is not an identity key. Denied or unsupported boot queries report their state without stopping process collection.

`nks_frame_get_network_transfer_data` returns bytes received and sent per network adapter since the monitor first observed it, with the start time. Totals add only non-negative deltas of the 64-bit interface octet counters; a counter decrease, an unavailable sample or a missing adapter restarts the baseline without adding traffic.

`nks_frame_get_session_data` lists the local WTS sessions (user, domain, window station, connection state and protocol) with CPU, working set, private memory and I/O totals over each session's processes, plus a session ID per process in frame order. WTS is queried only on the first call for a frame. A sum marks how many members had a current sample; the idle process is excluded. A session that only processes reveal is reported with unknown state, and a denied user query reports `ACCESS_DENIED` instead of an empty name. The WinUI Users view (Uživatelé) shows these totals and expands a session into its processes; per-process network traffic is not attributed yet, so the network column stays unavailable.
